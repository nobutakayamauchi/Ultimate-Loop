# The Three Destructions

Ultimate Loop is built around three different questions. They must not be collapsed into one generic review step.

## Loop 1 — Raison d’être Destroy

**Question:** Should this responsibility exist at all?

Attack the need before attacking an implementation.

```text
DROP
→ EXTERNALIZE
→ COMPOSE
→ MANUAL_BOUNDED
→ GLUE
→ IRREDUCIBLE_BUILD
```

Hard rule:

`NO SURVIVAL → NO BUILD`

A new build is justified only when a responsibility survives destruction and cannot be adequately discharged by existing capabilities, or when the existing architecture has a material deficit for the frozen workload.

This loop exists to prevent development from turning into infrastructure accumulation.

---

## Loop 2 — METEOR Crucible

**Question:** If the responsibility must exist, which implementation actually survives reality best?

Materialize realistic candidates and attack them under the same conditions.

The comparison can include:

- capability and output quality;
- reliability;
- failure behavior;
- security and privacy;
- operator burden;
- maintainability;
- cost;
- migration and rollback;
- provider/dependency risk;
- evidence maturity;
- recovery and reconstruction obligations.

A candidate does not win by deleting inherited safety, evidence, authority, durability, or recovery requirements.

Possible outcomes:

`KEEP / PARTIAL_REPLACE / FULL_REPLACE / STANDBY / REJECT`

`PROTOTYPE AUTHORIZED != PROMOTION AUTHORIZED`

---

## Loop 3 — DARWIN Arena

**Question:** Does the current promoted occupant still deserve its slot now?

Passing METEOR once never creates permanent entitlement.

A new match may be triggered by:

- a materially better challenger;
- a new model or algorithm;
- OS/platform/API change;
- OSS/SaaS/provider change;
- price or operator-burden change;
- security evidence;
- runtime failure;
- law/procedure change;
- a new failure class;
- an era change that invalidates old assumptions.

Possible outcomes:

`SURVIVE / RECOMPOSE / PARTIAL_REPLACE / FULL_REPLACE / DIE`

Every promoted implementation lives in a **Movable Frame**.

`IMPLEMENTED != PERMANENT`

---

## Why three loops?

They kill three different kinds of attachment:

1. **attachment to the need** — “we should build this”;
2. **attachment to the implementation** — “our version is the right one”;
3. **attachment to incumbency** — “it worked before, therefore it should stay.”

Ultimate Loop is not complete if any one of these three destructive pressures is missing.
