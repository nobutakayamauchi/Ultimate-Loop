# Ultimate Loop

> **百万回殺せ。なお立つものだけ作れ。**

**Ultimate Loop** is a self-evolving development method that decides:

- whether a responsibility deserves to exist at all;
- which implementation deserves to occupy that responsibility;
- whether the current implementation still deserves to survive when reality changes;
- and what evidence, memory, authority, and recovery path must remain when implementations, providers, tools, or even the original creator disappear.

It is **not** a framework, model, runtime, product, or provider.

Status: `PROVISIONAL_OPERATIONAL / CANONICAL / ACTIVE / SELF_EVOLVING`

Formal name: **Development Sequence Loop**  
Common name: **Ultimate Loop**

---

## The three destructions

Ultimate Loop was refined during the reconstruction that produced **RTS Evolution**. Its core is three destructive loops.

### 1. Raison d’être Destroy

**Should this responsibility exist at all?**

Before building, try to kill the need to build.

`DROP → EXTERNALIZE → COMPOSE → MANUAL_BOUNDED → GLUE → IRREDUCIBLE_BUILD`

**No survival, no build.**

### 2. METEOR Crucible

**If it must exist, which implementation actually survives reality best?**

Attack the strongest existing/external composition and the smallest justified custom candidate under the same frozen workload, evidence requirements, authority boundaries, destructive cases, recovery obligations, and whole-life criteria.

A benchmark win alone is not enough.

### 3. DARWIN Arena

**Even if it survived before, does the incumbent still deserve its slot now?**

Every promoted implementation remains replaceable. A credible challenger, material failure, provider change, cost shift, security event, or era change can reopen the match.

Possible outcomes include:

`SURVIVE / RECOMPOSE / PARTIAL REPLACE / FULL REPLACE / DIE`

No implementation receives a permanent right to exist.

Ultimate Loop is subject to its own rule.

`ULTIMATE LOOP != IMMORTAL`

`SUPERIOR PROTOCOL PROVEN → ULTIMATE LOOP YIELDS`
