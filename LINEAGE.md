# Lineage

Ultimate Loop did not begin as a standalone theory. It emerged from a sequence of destructive development experiments.

## 1. Original RTS

The original RTS accumulated responsibilities around evidence, authority, reconstruction, runtime reality, governance, recovery, and development continuity.

It eventually became a target of its own necessity question: which parts genuinely deserved to survive, and which parts existed only because the system had grown around itself?

## 2. WITNESS

WITNESS was first conceived as a new system for retaining only the parts that were actually necessary.

Then WITNESS itself was subjected to the same question:

**Does WITNESS need to exist as software at all?**

The answer under the final experiments was **no**.

The standing runtime/controller/platform was eliminated. What survived were five semantic protections:

1. Preserve the original requested outcome and completion conditions.
2. Preserve `UNKNOWN / CONFLICT`; missing proof must not become success.
3. Define what may become canonical project truth.
4. Require materially separated review for materially fallible completion judgments.
5. Preserve the fact and reason when a test, evaluator, observation, or implementation was defective.

Historical source: [WITNESS](https://github.com/nobutakayamauchi/WITNESS)

## 3. RTS Evolution

Those surviving principles were then used as part of a reconstruction experiment:

**Can RTS be reproduced from existing capabilities, while restoring only the responsibilities that survive necessity testing, and still become stronger than the old system?**

The answer was yes.

Instead of reviving the old monolithic architecture, existing systems were reused or composed wherever possible and bounded custom responsibility was added only when necessary. The resulting successor became **RTS Evolution**.

Current successor home: [RTS Evolution](https://github.com/nobutakayamauchi/RTS-Evolution)

Historical reconstruction evidence remains in: [RTS](https://github.com/nobutakayamauchi/RTS)

## 4. Ultimate Loop

While RTS Evolution was being reconstructed, the *development motion itself* became more explicit and repeatable.

Three distinct destructive loops emerged:

- **Raison d’être Destroy** — destroy the need to build;
- **METEOR Crucible** — destroy weak implementations;
- **DARWIN Arena** — destroy permanent incumbency.

Around those loops, additional disciplines were retained for current-landscape discovery, deployment identity, post-deploy reality checks, WATCH, emergency recovery, PHOENIX lineage, and creator-independent reconstruction.

That refined development method became **Ultimate Loop**.

## Compact lineage

```text
Original RTS
  ↓ necessity attack
WITNESS
  ↓ software necessity destroyed
Five principles survive
  ↓ reconstruction with existing capabilities + surviving responsibilities
RTS Evolution
  ↓ development motion itself is refined
Ultimate Loop
  ↓
current and future development
```

The lineage is intentionally not a claim that each later artifact permanently outranks every earlier one.

Ultimate Loop itself is replaceable. If a superior protocol is proven, the lineage continues through the successor.
